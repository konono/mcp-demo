## Decision 1: ビルドバックエンドに hatchling を採用

### 背景
単一モジュール `search_demo.py` のみのプロジェクトに pyproject.toml を追加する。パッケージ自動検出に任せると `.opencode` や `__pycache__` を拾う懸念がある。

### 選択肢
1. hatchling + `[tool.hatch.build.targets.wheel] only-include`
2. setuptools + `[tool.setuptools] py-modules = ["search_demo"]`
3. flit

### 採用した案
1（hatchling）

### 採用理由
- 単一モジュールの指定が `only-include = ["search_demo.py"]` の 1 行で済み、除外設定が不要
- PEP 621 準拠のメタデータをそのまま書ける
- 依存ゼロのプロジェクトに対してビルド依存も hatchling 1 つで最小

### 採用しなかった案と理由
- setuptools: `py-modules` で実現可能だが、自動検出との兼ね合いで `[tool.setuptools.packages.find]` の除外指定も書く必要が出やすく、設定が増える
- flit: 単一モジュールに適するがモジュール冒頭の docstring と `__version__` をメタデータ源にする規約があり、`search_demo.py` に `__version__` が存在しない（`grep` 結果で `version` に一致したのは `formatversion` のみ）ため追加改変が必要になる

### トレードオフ
hatchling はビルド時に追加ダウンロードが必要（stdlib のみという実行時の方針は維持されるが、ビルド時は依存が増える）。

### 見直し条件
プロジェクトが複数モジュール/パッケージ構成に成長した場合、または CI が setuptools 前提になった場合。

## Decision 2: Python ランタイムをインストールせず未検証のまま納品する

### 背景
ビルド検証をしたかったが、環境に Python も uv もない（Issue 1）。

### 選択肢
1. 未検証のまま納品し、未検証であることを明示する
2. `mise use python@3.12` を実行して Python を入れ、ビルド検証する
3. pyproject.toml の作成自体を保留してユーザーに確認する

### 採用した案
1

### 採用理由
- ユーザーの依頼は「pyproject.toml を作成してください」であり、ランタイム導入は依頼範囲外の環境変更
- 作成物自体は標準的な構成で、提供には十分な確度がある
- 検証していない事実を報告すれば、ユーザーが検証するか判断できる

### 採用しなかった案と理由
- 2: 環境に副作用（mise のバージョン設定、Python のダウンロード）が生じる。依頼されていない変更をしない方針に反する
- 3: 成果物を一切渡さずに止めるほどの不確実性ではない

### トレードオフ
pyproject.toml に構文エラーや hatchling 設定の誤りが残っている可能性を排除できない。

### 見直し条件
ユーザーがビルド検証も含めて依頼した場合、または Python が利用可能になった場合。

## Decision 3: Python を mise に追加せず uv のみ導入する

### 背景
ユーザーから「miseでuvいれてbuild検証してください」と依頼された。Issue 1 の時点では Python もビルドツールもなかったため、両方必要かを判断する必要があった。

### 選択肢
1. `mise use uv@latest` のみ
2. `mise use python@3.12 uv@latest`（README が言及する Python 3.12 も併せて入れる）

### 採用した案
1

### 採用理由
- ユーザーの依頼は「uv をいれて」であり、Python は指定されていない
- uv は必要な CPython を自前で取得するため、ビルドに Python の事前導入は不要（Finding 3 で実証）
- 導入するツールは少ないほうが `mise.toml` がシンプルになる

### 採用しなかった案と理由
- 2: 依頼されていないツールの追加になる。実際に試した結果 uv 単独でビルドが完遂したので、追加する理由が生じなかった。

### トレードオフ
`mise x -- python` が使えないままになる（Issue 2）。単発の Python 実行には `mise x -- uv run --no-project python` という一段長いコマンドが必要。README が案内する `mise x -- python search_demo.py` の手順も、現状の mise.toml のままでは動かない。

### 見直し条件
README の手順どおり `mise x -- python search_demo.py` を動かしたい場合は `mise use python@3.12` を追加する。

## Decision 4: uv のバージョンを "latest" のまま据え置く

### 背景
`mise use uv@latest` が `mise.toml` に `uv = "latest"` と書き込んだ。再現性の観点では具体バージョン（0.12.23）への固定が望ましい。

### 選択肢
1. `uv = "latest"` のまま
2. `uv = "0.12.23"` に固定

### 採用した案
1

### 採用理由
- ユーザーが指定したのは `mise でuvをいれる` ことで、バージョン方針の指示はない
- mise のデフォルト挙動をそのまま残すほうが、ユーザーが意図を変更しやすい
- 依頼範囲外の勝手な編集を避ける

### 採用しなかった案と理由
- 2: 再現性は上がるが、ユーザーの意図（常に最新を使いたいのかもしれない）を推測して勝手に変えることになる。報告時に選択肢として提示する方が適切と判断した。

### トレードオフ
将来 uv の破壊的変更でビルド挙動が変わっても気づきにくい。

### 見直し条件
CI でビルドを再現する必要が出た場合、またはユーザーが固定を希望した場合。

## Decision 5: sdist の絞り込みに only-include を使う

### 背景
Issue 3 で sdist に `.tracecraft/` と `.opencode/` が混入していることが判明した。

### 選択肢
1. `[tool.hatch.build.targets.sdist]` に `only-include` で許可リスト方式
2. 同セクションに `exclude = [".tracecraft", ".opencode", "__pycache__"]` で拒否リスト方式
3. `.gitignore` を作成し git リポジトリ化して hatchling の VCS 除外に任せる

### 採用した案
1

### 採用理由
- wheel ターゲットと同じ `only-include` 方式で揃い、設定が読みやすい
- 許可リストなので、今後新しいドットディレクトリやツール生成物が増えても自動的に除外される（拒否リストは追加のたびにメンテが必要）
- このプロジェクトは配布対象ファイルが 3 つしかないため、列挙コストが低い

### 採用しなかった案と理由
- 2: 除外対象を網羅し続ける必要があり、漏れたときに静かに混入する。今回まさにそれが起きた類の失敗。
- 3: git 化はユーザーの依頼範囲外の大きな変更。また `.gitignore` に頼ると配布物の内容が VCS 設定に暗黙依存することになる。

### トレードオフ
配布対象ファイルを追加したときに `only-include` の更新を忘れると、新ファイルが sdist に入らない。ただし入らない失敗は気づきやすく、入ってしまう失敗より安全。

### 見直し条件
配布対象ファイルが増えて列挙が煩雑になった場合は exclude 方式への切り替えを検討する。
