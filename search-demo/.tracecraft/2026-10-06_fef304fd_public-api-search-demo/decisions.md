## Decision: 標準ライブラリのみで実装する（requests / httpx を使わない）

### 背景
実行環境に Python 自体が無く（findings 1 件目）、デモを見る人の環境も揃っているとは限らない。

### 選択肢
1. `urllib.request` のみ（依存ゼロ）
2. `requests` / `httpx` + requirements.txt
3. uv の inline script metadata (PEP 723) で依存を宣言

### 採用した案
案 1（`urllib.request` のみ）。

### 採用理由
エージェント（opencode）が Skill からコマンドを実行する際、`pip install` の一段が挟まると失敗点が増える。デモでは「叩けば動く」ことが価値。

### 採用しなかった案と理由
案 2: インストール手順がデモの流れを止める。案 3: uv が未インストールの環境では動かず、依存ゼロという利点も相殺される。

### トレードオフ
得たもの: セットアップ不要、どの Python 3.10+ でも動く。失った/注意すべき点: リトライ・コネクションプール・HTTP/2 等は自前実装が必要で、本スクリプトでは実装していない。タイムアウトは 10 秒固定。

### 見直し条件
リトライや認証ヘッダ管理が必要になった時点で httpx への移行を検討する。

## Decision: 部分的な失敗を例外にせず errors 配列で返す

### 背景
4 ソースを並列に叩くため、1 つのレート制限超過で全体が落ちるとデモが成立しない。

### 選択肢
1. 最初の失敗で例外を投げて終了
2. ソース単位で捕捉し、成功分 + `errors` を返す
3. 失敗を無視して成功分だけ返す

### 採用した案
案 2。全ソース失敗かつ結果 0 件のときのみ終了コード 1。

### 採用理由
エージェントが部分結果で回答を続けられる。同時に、何が取れなかったかを `errors` から認識できるので黙殺にならない。

### 採用しなかった案と理由
案 1: GitHub のレート制限は未認証だと容易に当たるため脆すぎる。案 3: 失敗が不可視になり、エージェントが「情報が無い」と誤認する。

### トレードオフ
得たもの: 堅牢性と透明性。注意点: 呼び出し側が `errors` を読まないと欠落に気付けないため、SKILL.md に「count が 0 のときは errors を読む」と明記した。

### 見直し条件
ソース数が増えて errors が常時ノイズになる場合、重要度に応じた扱い分けを検討する。

## Decision: 出力の既定を JSON にする

### 背景
主な呼び出し元はエージェントだが、デモ中に人間が目で見る場面もある。

### 選択肢
1. 既定 text、`--format json` で切替
2. 既定 JSON、`--format text` で切替

### 採用した案
案 2。

### 採用理由
本スクリプトの一次利用者は opencode のエージェントであり、パースしやすさを優先する。人間確認は `-f text` で足りる。

### 採用しなかった案と理由
案 1: エージェントが毎回フラグを付ける必要があり、付け忘れでパース失敗を招く。

### トレードオフ
得たもの: エージェントからの利用が確実。失ったもの: 素で叩いたときの可読性（`-f text` で回避可能）。

### 見直し条件
CLI として人間が日常利用するようになった場合は TTY 判定による自動切替を検討する。
